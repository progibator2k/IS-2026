### Обоснование выбора

#### 1. Почему клиент–сервер подходит для этой задачи?

Система — это **внутренняя корпоративная информационная система** авиастроительного предприятия. Пользователи — сотрудники разных ролей: начальники цехов, технологи, испытатели, кадровики — все работают через браузер с рабочего места. Они делают аналитические запросы (14 видов запросов, указанных в ТЗ): получить перечень изделий, кадровый состав, список лабораторий и т.д.

Клиент–сервер идеально ложится на эту модель: **один бэкенд** обслуживает всех пользователей через единый REST API, а тонкий веб-клиент только отображает данные. При этом:
- Бизнес-логика и доступ к данным сосредоточены на сервере — легче обеспечить безопасность (роли, права доступа)
- Данные не хранятся на клиенте — критично для оборонного предприятия
- Легко добавить нового клиента (например, планшетный интерфейс для бригадиров в цеху) — бэкенд не меняется

#### 2. Почему отказались от альтернатив?

**Отвергнутый вариант — Микросервисы.**

Микросервисная архитектура потребовала бы разбить систему на отдельно развёртываемые сервисы (например: `ProductsService`, `PersonnelService`, `TestingService`, `WorkshopService`). Это создаёт следующие проблемы в данном контексте:

- **Небольшое число пользователей** (~200 человек предприятия) — нет нагрузки, при которой микросервисы дали бы выигрыш
- **Нет команды для поддержки** — микросервисы требуют DevOps-инфраструктуры (Kubernetes, service mesh, distributed tracing), что оверинжиниринг для корпоративной ИС
- **Сильная связность данных** — запрос №2 («перечень изделий, собранных цехом/участком/предприятием за период») требует JOIN между таблицами изделий, участков, цехов — в микросервисах это превратилось бы в цепочку сетевых вызовов между сервисами, что сложнее и медленнее одного SQL-запроса

#### 3. Минусы выбранного стиля и как с ними жить

| Минус | Как живём |
|---|---|
| Единая точка отказа (один сервер) | Nginx + supervisor для автоперезапуска процессов; резервное копирование БД ежедневно |
| При росте нагрузки нужно масштабировать весь сервер целиком | Приемлемо: DAU ~200 чел., один сервер справится (см. Раздел 3) |
| Всё падает вместе, если бэкенд недоступен | Для внутренней корпоративной системы с рабочим временем 8–17 это приемлемо |

#### Условие перехода на другой стиль

**Переход на микросервисы** оправдан если:
- Предприятие вырастает до холдинга из 5+ заводов, DAU превышает 5 000 человек
- Появляются мобильные приложения для бригадиров с real-time обновлениями статуса сборки (нужен отдельный WebSocket-сервис)
- Разные команды начинают независимо развивать модули «Кадры» и «Производство»

### Описание компонентов

#### 1. Web SPA (React + TypeScript) — Клиент
**Что делает:** Отрисовывает пользовательский интерфейс: таблицы с изделиями, формы фильтрации, отчёты по 14 видам запросов. Отправляет REST-запросы к бэкенду, отображает ответы.

**Почему нужен именно здесь:** У системы — несколько ролей пользователей с разными интерфейсами. SPA позволяет строить богатый интерфейс без перезагрузки страниц. Начальнику цеха нужно видеть живой список изделий на участке (запрос №8/14), а не ждать полной перезагрузки.

---

#### 2. Nginx — Обратный прокси
**Что делает:** Принимает все входящие HTTPS-запросы, отдаёт статику (HTML/JS/CSS) напрямую, проксирует API-запросы к бэкенду. Обрабатывает SSL-сертификаты.

**Почему нужен именно здесь:** Бэкенд (FastAPI/Uvicorn) не предназначен для прямой работы с интернетом — Nginx закрывает его от внешнего мира, берёт на себя TLS и эффективно раздаёт статические файлы SPA без лишней нагрузки на Python-процесс.

---

#### 3. Backend API (FastAPI + Python) — Сервер
**Что делает:** Реализует бизнес-логику: обрабатывает все 14 видов запросов, проверяет права доступа по роли пользователя, валидирует данные, формирует SQL-запросы к БД, возвращает JSON-ответы.

**Почему нужен именно здесь:** Центральный компонент, содержащий всю логику. Разделён на модули по предметной области:
- `workshops` — цеха и участки
- `products` — изделия и их категории (самолёты, ракеты и т.д.) с полиморфными атрибутами
- `personnel` — персонал, бригады, движение кадров
- `testing` — испытательные лаборатории, оборудование, испытатели
- `reports` — аналитические запросы 1–14
- `auth` — аутентификация и авторизация по ролям

---

#### 4. PostgreSQL — Основная база данных
**Что делает:** Хранит все данные системы: иерархию предприятия (цеха → участки), изделия и их производственные циклы, персонал и бригады, испытания и лаборатории.

**Почему нужен именно здесь:** Данные глубоко реляционные — запрос №2 требует связать изделие → участок → цех → предприятие с фильтрацией по периоду. Это сложные JOIN, для которых реляционная СУБД с индексами — единственный разумный выбор. PostgreSQL поддерживает полиморфизм через наследование таблиц (категории изделий с разными атрибутами) или JSONB-колонки для специфичных полей.

---

#### 5. Redis — Кэш аналитических запросов
**Что делает:** Кэширует результаты тяжёлых аналитических запросов с ограниченным TTL.

**Почему нужен именно здесь:** Конкретные случаи, когда без кэша плохо:
- **Запрос №2/11** — «перечень изделий за определённый период» требует агрегации по большим таблицам с историческими данными (за год накапливаются сотни изделий, тысячи записей о перемещениях). Один и тот же отчёт «за 2025 год по цеху №3» может запрашиваться разными менеджерами 20 раз в день — без кэша это 20 одинаковых тяжёлых запросов к БД.
- **Запрос №3** — кадровый состав предприятия меняется редко (раз в несколько дней), но запрашивается часто. Кэш с TTL=1 час исключает лишние запросы к БД.

Кэш **не нужен** для запросов о текущем состоянии (запрос №8/14 — что собирается прямо сейчас) — там данные меняются в реальном времени и кэш только навредит.

## Раздел 3 — Оценка нагрузки

### Исходные данные

**DAU (Daily Active Users):**
Авиастроительное предприятие — это закрытая корпоративная система. Типовая численность: 5–10 цехов × 5–10 участков каждый, инженерно-технический персонал + кадровики + руководство.

```
Оценка DAU = 200 человек
(~50 начальников/мастеров + ~80 инженеров/технологов + 
 ~30 кадровиков/испытателей + ~40 бригадиров)
```

---

### Действия пользователей в день

| Роль | Действия | Запросов/день на пользователя |
|---|---|---|
| Начальник цеха/участка | Смотрит статус изделий, список бригад, текущую сборку | ~30 |
| Технолог | Просматривает циклы работ, отчёты за период | ~20 |
| Кадровик | Кадровый состав, движение кадров | ~15 |
| Испытатель | Список лабораторий, оборудование, протоколы | ~20 |
| Руководство | Сводные отчёты | ~10 |

**Средневзвешенное**: ~20 запросов на пользователя в день

---

### Расчёт RPS

```
Рабочий день: 8 часов = 28 800 секунд
Пиковые часы: утро 9:00–11:00 (начало смены + планёрки) = 2 часа

Общее число запросов/день:
  200 пользователей × 20 запросов = 4 000 запросов/день

Средний RPS (равномерно за 8 часов):
  4 000 / 28 800 ≈ 0.14 RPS

Пиковый RPS (60% запросов за 2 часа = 7 200 сек):
  4 000 × 0.6 / 7 200 ≈ 0.33 RPS

С коэффициентом × 3 (всплески):
  Пиковый RPS = 0.33 × 3 ≈ 1 RPS
```

---

### Оценка объёма данных

**Размер основных записей:**
```
Запись об изделии:          ~2 KB  (атрибуты + специфика категории)
Запись об операции сборки:  ~0.5 KB
Запись о персонале:         ~1 KB
Запись об испытании:        ~1 KB
```

**Прирост данных в день:**
```
Новые изделия в сборке:     ~3 шт × 2 KB  =   6 KB
Обновления статуса сборки:  ~50 × 0.5 KB  =  25 KB
Изменения персонала:        ~5 × 1 KB     =   5 KB
Записи об испытаниях:       ~5 × 1 KB     =   5 KB
Итого в день:               ≈ 41 KB/день
```

**За год:**
```
41 KB × 365 = ~15 MB/год (только новые данные)
+ исторические данные за 10 лет работы предприятия ≈ 150 MB
Итого БД с запасом ×10 (индексы, WAL, резервы): ≈ 2 GB
```

---

### Вывод

**Один сервер полностью справляется.** Обоснование:

- **1 RPS пиковой нагрузки** — современный FastAPI-сервер обрабатывает 500–2000 RPS. Текущая нагрузка составляет **0.05%** от возможностей
- **2 GB данных** — стандартный сервер с SSD в 100 GB хранит данные на 50+ лет вперёд
- **200 одновременных пользователей** — PostgreSQL легко обслуживает 100–200 соединений без деградации

**Горизонтальное масштабирование не нужно.** Потребуется только при росте DAU до 5 000+ человек (объединение нескольких заводов в холдинг) или при появлении real-time компонентов (IoT-датчики с оборудования в цехах, стримящие данные каждую секунду).

## Раздел 4 — Выбор стека технологий

### Бэкенд: **Python + FastAPI**

**Что выбрали:** Python 3.11 + FastAPI + Uvicorn

**Почему подходит:**
- Система делает много аналитических запросов (14 типов из ТЗ) — Python хорошо подходит для логики агрегации и трансформации данных перед отдачей клиенту
- FastAPI автоматически генерирует OpenAPI-документацию — критично, когда нужно описать 14+ эндпоинтов для разных запросов и показать заказчику
- FastAPI поддерживает **async/await** — при параллельных запросах нескольких пользователей к тяжёлым отчётам не блокирует поток
- Pydantic (встроен в FastAPI) обеспечивает строгую валидацию входных данных — важно для фильтров по периодам, категориям изделий

**Альтернатива — Java + Spring Boot:** Отказались, потому что для команды из 1–2 разработчиков Spring Boot создаёт избыточный бойлерплейт. Скорость разработки прототипа в Python в 2–3 раза выше, а производительности Python достаточно при нагрузке в 1 RPS.

---

### База данных: **PostgreSQL 15**

**Что выбрали:** PostgreSQL 15

**Почему подходит:**
- Данные системы **строго реляционные**: Изделие → принадлежит Цеху → собирается на Участке → Бригадой → проходит Цикл Работ → испытывается в Лаборатории. Это цепочки JOIN от 4 до 6 таблиц — PostgreSQL оптимизирует их лучше, чем любая NoSQL-база
- Запросы типа «перечень изделий за период» (запрос №2) требуют **оконных функций** и **CTE** — PostgreSQL поддерживает их нативно
- Полиморфизм категорий изделий (самолёты, ракеты, вертолёты — у каждого свои атрибуты): решается через **наследование таблиц PostgreSQL** или через JSONB-колонку для специфичных атрибутов. Пример: `products` — базовая таблица, `products_airplane` (число двигателей), `products_rocket` (мощность заряда)
- **ACID-транзакции** — важны при записи результатов испытания: нужно атомарно обновить статус изделия, записать оборудование и испытателей

**Альтернатива — MongoDB:** Отказались, потому что, несмотря на удобство хранения полиморфных атрибутов изделий, MongoDB плохо справляется с многотабличными JOIN-запросами. Запрос «получить перечень изделий, собранных участком X за период Y, с бригадами и мастерами» в MongoDB превратился бы в несколько `$lookup` с плохой производительностью.

---

### Фронтенд: **React + TypeScript + Ant Design**

**Что выбрали:** React 18 + TypeScript + Ant Design (UI-библиотека)

**Почему подходит:**
- **Ant Design** — библиотека корпоративных компонентов: готовые таблицы с пагинацией, фильтрами, экспортом в Excel — это именно то, что нужно для вывода 14 видов отчётов (перечни изделий, кадровый состав и т.д.)
- **TypeScript** — строгая типизация предотвращает ошибки при работе с разными типами ответов API (изделия разных категорий имеют разные поля)
- React подходит для SPA с несколькими разделами (Производство / Кадры / Испытания / Отчёты) без перезагрузки страниц

**Альтернатива — Vue.js:** Рассматривали, но Ant Design имеет более богатую экосистему именно для React, а корпоративные таблицы (AntD Table с серверной пагинацией) — ключевой компонент всего интерфейса.

---

### Кэш: **Redis 7**

**Что выбрали:** Redis 7 (in-memory key-value store)

**Почему подходит:**
- Конкретный кейс: аналитический запрос «перечень изделий цеха №3 за 2024 год» занимает ~200 мс (JOIN 5 таблиц + агрегация по периоду). При 10 одновременных пользователях это 2 секунды суммарной нагрузки на БД. Redis позволяет ответить за 1–2 мс, взяв результат из памяти
- TTL 30 минут для исторических отчётов (за прошлые периоды данные не меняются)
- TTL 0 (не кэшируем) для запросов реального времени (#8, #14 — что собирается сейчас)

**Альтернатива — Memcached:** Отказались в пользу Redis, потому что Redis поддерживает **сложные структуры данных** и **TTL на уровне ключа** — это удобнее для кэширования отчётов с разными ключами (цех + период + категория изделия).

```
│  извлекает параметры (workshop_id, period,    │

│  передаёт в Service, возвращает JSON-ответ    │
│                                               │
│  Пример: GET /api/products?workshop=3         │
│          &category=airplane&date_from=...     │
└───────────────────┬───────────────────────────┘
                    │ вызов метода сервиса
                    ▼
┌───────────────────────────────────────────────┐
│              СЛОЙ СЕРВИСОВ                    │
│  (Business Logic Layer)                       │
│                                               │
│  Что делает: содержит бизнес-логику.          │
│  Например: определяет, какие таблицы          │
│  задействовать для запроса по категории       │
│  изделий (airplane → products_airplane),      │
│  формирует фильтры, проверяет права доступа   │
│  пользователя к конкретному цеху/участку,     │
│  проверяет кэш Redis перед запросом к БД      │
└───────────────────┬───────────────────────────┘
                    │ вызов метода репозитория
                    ▼
┌───────────────────────────────────────────────┐
│              СЛОЙ РЕПОЗИТОРИЕВ                │
│  (Data Access Layer)                          │
│                                               │
│  Что делает: SQL-запросы к PostgreSQL через   │
│  SQLAlchemy ORM. Только работа с данными —    │
│  никакой логики.                              │
│  Пример: get_products_by_workshop_and_period  │
│  строит SQL JOIN: products → workshops →      │
│  sections → assembly_cycles                   │
└───────────────────┬───────────────────────────┘
                    │ SQL
                    ▼
             [PostgreSQL]
```

### Пример взаимодействия слоёв для запроса №2

**«Получить перечень изделий категории "самолёт", собранных цехом №3 за 2024 год»**

```
GET /api/reports/products?workshop_id=3&category=airplane
                         &date_from=2024-01-01&date_to=2024-12-31

Router (products/router.py):
  └─ Извлечь: workshop_id=3, category="airplane", period=(2024-01-01, 2024-12-31)
  └─ Pydantic валидация: date_from < date_to ✓
  └─ Вызвать: products_service.get_by_workshop_and_period(...)

Service (products/service.py):
  └─ Проверить права: текущий пользователь имеет доступ к цеху №3? ✓
  └─ Проверить Redis: cache["products:workshop=3:cat=airplane:2024"] → MISS
  └─ Вызвать: products_repo.get_products(workshop_id=3, category="airplane", ...)

Repository (products/repository.py):
  └─ SQL:
     SELECT p.id, p.name, pa.engine_count, s.start_date, s.end_date
     FROM products p
     JOIN products_airplane pa ON pa.product_id = p.id
     JOIN assembly_cycles s ON s.product_id = p.id
     JOIN sections sec ON sec.id = s.section_id
     JOIN workshops w ON w.id = sec.workshop_id
     WHERE w.id = 3
       AND s.end_date BETWEEN '2024-01-01' AND '2024-12-31'
     ORDER BY s.end_date DESC;

Service (обратно):
  └─ Сохранить результат в Redis с TTL=30 мин
  └─ Вернуть список изделий

Router (обратно):
  └─ JSON-ответ: [{id, name, engine_count, assembled_at, ...}, ...]
```
