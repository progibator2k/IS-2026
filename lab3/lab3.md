# Анализ бизнес-процессов AS-IS
# ЗАДАНИЕ 1 — Определение процессов
## 🔷 Основной процесс: «Обработка заказа клиента»

| Параметр | Описание |
|---|---|
| **Цель процесса** | Обеспечить полный цикл обработки заказа: от оформления клиентом до доставки и закрытия |
| **Инициатор** | Клиент (покупатель) |
| **Входные данные** | Данные клиента, перечень выбранных товаров, адрес доставки, способ оплаты |
| **Выходные данные** | Доставленный и принятый заказ, закрытый счёт, обновлённые складские остатки |
| **Участники** | Клиент, менеджер по заказам, кладовщик, бухгалтер, служба доставки |
| **Ожидаемый результат** | Клиент получает заказанные товары в указанные сроки; заказ закрыт в системе |

---

## 🔶 Вспомогательный процесс 1: «Управление складскими запасами»

| Параметр | Описание |
|---|---|
| **Цель процесса** | Поддерживать актуальность сведений о наличии товаров и своевременно пополнять запасы |
| **Инициатор** | Кладовщик / система автоматического мониторинга остатков |
| **Входные данные** | Данные о поступлении товаров от поставщиков, данные об отгрузке по заказам, текущие остатки |
| **Выходные данные** | Обновлённые остатки в системе, заявки на пополнение запасов, акты приёмки |
| **Участники** | Кладовщик, менеджер по закупкам, поставщик, бухгалтер |
| **Ожидаемый результат** | Актуальный учёт товаров на складе; отсутствие критического дефицита позиций |

---

## 🔶 Вспомогательный процесс 2: «Обработка возвратов и рекламаций»

| Параметр | Описание |
|---|---|
| **Цель процесса** | Принять и обработать запрос клиента на возврат товара или рассмотреть претензию |
| **Инициатор** | Клиент (покупатель) |
| **Входные данные** | Заявка на возврат, причина обращения, номер заказа, документы (фото брака, чек) |
| **Выходные данные** | Решение по заявке (возврат средств / замена товара / отказ), обновлённые данные склада |
| **Участники** | Клиент, менеджер по работе с клиентами, бухгалтер, кладовщик |
| **Ожидаемый результат** | Закрытая рекламация, удовлетворённость клиента, корректный возврат средств или замена |

# ЗАДАНИЕ 3 — Анализ проблем основного процесса

| № | Возможная проблема | Причина | Последствие |
|---|---|---|---|
| 1 | **Ручная проверка наличия товаров** (узкое место) | Отсутствует автоматическая интеграция между витриной сайта и складской системой; менеджер проверяет остатки вручную через звонок/email на склад | Задержка подтверждения заказа до нескольких часов; клиент долго ожидает ответа; высокая нагрузка на менеджера |
| 2 | **Ручное подтверждение заказа менеджером** (ручная операция / задержка) | Нет автоматической системы валидации и подтверждения заказов; всё проходит через одного сотрудника | Бутылочное горлышко при высокой нагрузке; заказы накапливаются в очереди; клиент не получает подтверждение вовремя |
| 3 | **Дублирование ввода данных о заказе** (избыточность ввода) | При передаче заказа от менеджера к складу и затем к бухгалтерии данные вносятся повторно в разные системы (CRM, складская программа, Excel) | Потеря времени сотрудников; высокий риск ошибок при перепечатке; несоответствие данных в разных системах |
| 4 | **Отсутствие автоматических уведомлений клиенту о статусе заказа** (ручная операция / риск) | Уведомления отправляются менеджером вручную по электронной почте без использования триггерных рассылок | Клиент не знает текущего состояния заказа; поступает избыточное количество звонков в поддержку с вопросом «где мой заказ?» |
| 5 | **Передача заявки на склад по неформальным каналам** (риск / задержка) | Заявка на сборку передаётся по телефону или email, а не через систему управления складом (WMS) | Риск потери заявки; ошибки при устной передаче; невозможность отследить статус сборки; задержка отгрузки |
| 6 | **Фиксация оплаты дублируется в Excel** (дублирование операций / избыточность) | Бухгалтер фиксирует факт оплаты как в учётной системе (1С), так и в отдельной таблице Excel для оперативного учёта | Несогласованность данных; двойная работа бухгалтера; риск расхождения отчётности |
| 7 | **Отсутствие контроля над статусом доставки** (риск / задержка) | Нет интеграции с API транспортных компаний; менеджер узнаёт о доставке только после звонка курьера | Невозможность оперативно реагировать на задержки; клиент самостоятельно звонит для уточнения; репутационные потери |
| 8 | **Закрытие заказа и обновление остатков склада — отдельные ручные операции** (дублирование / ручная операция) | Закрытие заказа в CRM и обновление складских остатков выполняются раздельно разными сотрудниками без автоматической синхронизации | Расхождение реальных остатков с данными в системе; возможны повторные продажи уже отсутствующего товара |

```
                      ⚠️ P1                  ⚠️ P2           ⚠️ P6       ⚠️ P5      ⚠️ P7        ⚠️ P8
                      ⚠️ P3 (дублирование данных по всей цепочке)
                      ⚠️ P4 (отсутствие уведомлений по всей цепочке)

Легенда:
⚠️ P1 — Ручная проверка наличия товаров
⚠️ P2 — Ручное подтверждение заказа
⚠️ P3 — Дублирование ввода данных
⚠️ P4 — Отсутствие автоуведомлений
⚠️ P5 — Неформальная передача на склад
⚠️ P6 — Дублирование фиксации оплаты
⚠️ P7 — Нет контроля доставки
⚠️ P8 — Ручное закрытие/обновление остатков
```

---

> **Общий вывод по AS-IS:** Основной процесс обработки заказа характеризуется высокой долей ручных операций, отсутствием автоматической интеграции между подсистемами (сайт, CRM, склад, бухгалтерия, доставка), а также значительным дублированием данных. Это приводит к замедлению обработки, росту вероятности ошибок и снижению удовлетворённости клиентов. Выявленные проблемы станут основой для проектирования модели TO-BE.
